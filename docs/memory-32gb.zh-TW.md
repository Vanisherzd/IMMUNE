# 在 32 GB 記憶體上執行 IMMUNE

[English](memory-32gb.md) | **繁體中文**

原型設備有 122.8 GB 記憶體，整套系統用了約 46 GB。這份規劃說明怎麼把同一個修復迴圈放進**總記憶體只有 32 GB**（29.8 GiB）、CPU 與加速器共用記憶體的機器。安全路徑一律不縮減。

以下單位都是 GiB。標「實測」的數字來自原型設備；標「預算」的是目標值，要用最後一節的驗證步驟確認。

## 1. 記憶體用在哪裡

| 項目 | 大小 | 來源 |
|---|---|---|
| 模型權重（30B 級 MoE、3B active、4-bit） | 17.8 | 實測 |
| KV cache 預留（8-bit KV） | ≈10 | 實測；可放 41 條 32k token 的序列 |
| Reranker sidecar | 2.8 | 實測（RSS） |
| 社群知識索引（158,881 筆，SQLite FTS5） | 幾 MB | 實測 |
| 其他：作業系統、agent 沙箱、guardrails、各服務、測試容器、推論引擎額外開銷 | ≈12 | 46 GB 總量扣掉上面幾項，尚未逐項拆分 |

規劃建立在兩個觀察上：

1. **KV 預留比實際需要大了約 20 倍。** 推論引擎最多同時跑 2 條序列，預留卻放得下 41 條完整的 32k 序列。2 條序列大約只需要 0.5 GiB。
2. **模型權重是唯一不換模型就縮不下來的部分。** 其他項目不是靠設定就能縮小，就是可以量測後加上限。

## 2. 兩種配置

| 項目 | 配置 A：同級模型 | 配置 B：較小模型 |
|---|---|---|
| 模型權重 | 17.8 | ≤ 8（8–14B dense 或小型 MoE，4-bit） |
| KV cache，2 條序列，8-bit | 1.5 | 1.5 |
| 推論引擎額外開銷（activation、graph） | 1.5 | 1.5 |
| Reranker | 關閉 | 2.8 |
| 作業系統 | 1.5 | 1.5 |
| Agent 執行環境與沙箱 | 1.5 | 1.5 |
| Guardrails 服務 | 1.0 | 1.0 |
| Ops API、watchdog、審核、審批、操作台 | 0.5 | 0.5 |
| 被測試的目標服務 | 0.5 | 0.5 |
| **合計** | **25.8** | **18.8** |
| **29.8 剩下的餘裕** | **4.0** | **11.0** |

配置 A 保留產出實測成績的那一級模型，但餘裕很薄。配置 B 讓所有選用層都能開，但要重跑修復測試，因為較小的模型可能拉低修復率。

先試配置 A；如果過不了第 4 節的記憶體檢查，再改用 B。

## 3. 設定

**推論**
- 最多 2 條同時序列，context 最多 32k token，KV 用 8-bit。
- KV 池依這 2 條序列配置（約 1.5 GiB），不要用總記憶體的百分比。
- 檢查載入模型時的峰值。如果推論引擎先把權重讀進 page cache 再複製到加速器，載入時會短暫需要兩份（配置 A 約 36 GiB），超過整台機器的記憶體。改用串流載入，或載入後清掉 page cache。
- 一次只跑一個推論服務。原型設備上同時開兩個推論服務曾讓整台機器當掉。
- 事先編譯 kernel，並限制平行工作數（例如 `MAX_JOBS=4`）。原型設備上不限數量的平行編譯曾讓機器卡死。

**選用層：交給 resource governor 管理**
- 開啟 `RESOURCE_GOVERNOR=1`。[`scripts/resource_governor.py`](../scripts/resource_governor.py) 會讀 `MemAvailable` 並選擇模式：

  | 模式 | 平行專家 | Reranker | 社群語料 |
  |---|---|---|---|
  | full | 2 | 開 | 大 |
  | reduced | 1 | 開 | 小 |
  | minimal | 0 | 關 | 小 |

- 預設門檻（`GOV_FULL_GB=20`、`GOV_REDUCED_GB=8`）是為大記憶體機器設的。32 GB 先用 `GOV_FULL_GB=8`、`GOV_REDUCED_GB=4`，量測後再調整。
- Governor 永遠不會限制主 agent 和安全路徑。

**防止記憶體耗盡**
- 每個服務都設記憶體上限（systemd 的 `MemoryMax=`、Docker 的 `--memory`）。超過上限的服務會被單獨停掉，不會拖垮整台機器。
- 替安全路徑保留記憶體（ops API、guardrails、watchdog、審批設 `MemoryMin=`）。
- 加一小塊壓縮 swap（zram，4–8 GiB）吸收短暫尖峰，不拿來放模型權重。
- 設定記憶體不足時的停止順序：先停 reranker，再停操作台。永遠不停 ops API、guardrails、watchdog 和審批。

**永遠不縮減的部分**
- 政策閘、白名單、guardrails、雙鑰審核、人工審批、驗證、稽核紀錄、事故記憶。

## 4. 驗證

每一步都在 32 GB 的機器上跑，並用 [`scripts/mem-profile.sh`](../scripts/mem-profile.sh) 記錄每個服務與容器的記憶體。

| 步驟 | 檢查內容 | 通過條件 |
|---|---|---|
| 1. 拆分 | 量測目前整套系統閒置與演練時的記憶體 | 「其他」那一列拆成逐項數字 |
| 2. 載入 | 只啟動推論服務 | 峰值低於 28 GiB |
| 3. 穩定狀態 | 啟動整套系統 | 配置 A 的 `MemAvailable` ≥ 4 GiB，配置 B ≥ 8 GiB |
| 4. 壓力測試 | 跑同樣 15 種故障、27 場演練 | `MemAvailable` 始終不低於 2 GiB；安全路徑的服務沒有被停掉 |
| 5. 品質 | 和原型設備比較 | 修復率接近 27 場 23 場；越修越壞 0 場；謊報健康 0 次；注入指令 3/3 擋下 |
| 6. 速度 | 三個示範故障從開事故到恢復的時間 | 和 32–85 秒比較並回報 |

判斷方式：配置 A 通過步驟 2–4，就繼續用 A 並完成 5–6。A 在步驟 2–4 失敗，就改用 B，從步驟 2 重來。B 在步驟 5 不及格，就在同一套測試上比較幾個候選模型再決定。

## 5. 如果加速器有自己的記憶體

如果模型跑在有獨立記憶體的加速器上，32 GB 系統記憶體只需要放模型與 KV cache 以外的部分。實測剩餘約 12 GiB，加上 2.8 GiB 的 reranker，完整配置不用上面的縮減就放得下。只有加速器本身的記憶體需要套用第 3 節的推論設定。
